## 1. 目标、边界与实施原则

### 1.1 后端目标

将现有高完成度前端原型升级为具备真实账号、数据同步、匿名公开、服务端积分结算和可审计安全边界的 v1 产品。

首发闭环：

```text
预置桌宠试玩
  → 倒地触发登录
  → 注册赠送免费 DIY + 300 积分
  → 桌宠互动 / 签到 / 关怀 / 吐槽 / 共鸣赚分
  → 积分复活领导
  → 吐槽销毁释怀
```

### 1.2 不在本期后端范围

- 真实支付、会员、积分商城、积分交易或提现；
- 评论、私信、关注、排行榜、热度排序；
- 私密吐槽、吃瓜/热榜；
- 手机号、邮箱绑定及其找回流程；
- 客户端自定义积分值、浏览器直写业务表。

### 1.3 实施基线（当前建议）

采用 **Supabase** 作为 v1 后端基线：Postgres + Auth + Row Level Security（RLS）+ Edge Functions + 定时任务。

选择理由：需求已明确使用“RLS / Edge Function / RPC”边界，且产品需要匿名公开查询、复杂原子积分结算、到期清理和访问控制。若后续改用自建 Node/NestJS 服务，本文的表结构、接口契约、权限与验收规则仍然适用，只需将 Function/RPC 实现迁移到 API 服务。

### 1.4 硬性原则

1. 浏览器只能报告行为，服务端决定状态、积分与奖励资格。
2. 所有积分变更写入不可由客户端伪造的 `point_ledger` 流水。
3. 所有可重试写操作携带幂等键；数据库负责最终唯一性。
4. 公开吐槽接口绝不返回账号、`owner_id`、审核字段、销毁凭证或恢复码相关数据。
5. 密码和恢复码仅保存成熟算法生成的哈希；日志禁止记录明文。
6. RLS 默认拒绝，公开读取仅经受限视图/RPC，关键写操作仅经 Function/RPC。
7. 所有每日上限以服务端配置的自然日与时区为准；客户端时间仅作展示。

## 4. 身份与账号设计（M1）

### 4.1 身份模型

- 对外字段名称统一为“账号”；趣味文案可称“牛马编号”或“摸鱼代号”。
- 账号规则：4–20 位，`a-z` / `A-Z` / `0-9` / `_`；全局唯一；存储时保留展示值并维护标准化唯一值。
- 密码：8–32 位，字母、数字、符号任意两类；不要求固定周期修改。
- 不绑定手机、邮箱、昵称或头像。
- 账号不出现在任何公开查询、吐槽卡、公共响应和审计日志中。

### 4.2 推荐实现

Supabase Auth 原生以邮箱/手机号为核心。为满足“账号 + 密码、无邮箱”的产品要求，使用受控的 Edge Function 注册/登录入口，并建立 `account_credentials` 映射表：

- 账号标准化值仅存在受限表；
- 服务端使用不可逆、内部派生的登录标识创建 Auth 用户；
- 前端永远只传账号和密码；
- 派生标识、恢复码、密码不返回前端日志；
- Service Role Key 仅在 Edge Function 环境中使用，绝不进入前端。

> 实现开始前必须确认 Supabase Auth 当前版本支持的管理员创建、密码校验与匿名账号策略；若存在限制，则用独立认证服务或自建认证表替代，但不得降低密码哈希与会话安全要求。

### 4.3 恢复码

- 注册成功生成一次高强度恢复码，例如 `XQX-xxxx-xxxx-xxxx-xxxx`；明文只在本次响应中出现。
- 数据库存储恢复码哈希、生成时间、使用/作废时间；不可回读明文。
- 找回密码提交 `account + recovery_code + new_password`；成功后原恢复码失效，并生成新的恢复码。
- 密码和恢复码同时丢失时拒绝找回，管理员不得绕过认证接管账号。

### 4.4 M1 接口契约

#### `POST /functions/v1/auth-register`

请求：

```json
{
  "account": "workhorse_01",
  "password": "example-password",
  "request_id": "uuid"
}
```

成功响应：

```json
{
  "ok": true,
  "access_token": "...",
  "refresh_token": "...",
  "profile": { "points_balance": 300, "free_diy_available": true },
  "recovery_code": "XQX-..."
}
```

约束：账号唯一；`request_id` 幂等；注册成功原子初始化 M2 所需档案与欢迎积分；恢复码只在这一响应出现一次。

#### `POST /functions/v1/auth-login`

请求：`{ "account": "workhorse_01", "password": "..." }`

响应：`{ "ok": true, "access_token": "...", "refresh_token": "...", "profile": { ... } }`

失败统一返回模糊的 `invalid_credentials`，不泄露账号是否存在。接口按账号、IP、设备维度限流。

#### `POST /functions/v1/auth-reset-password`

请求：

```json
{
  "account": "workhorse_01",
  "recovery_code": "XQX-...",
  "new_password": "...",
  "request_id": "uuid"
}
```

成功响应：`{ "ok": true, "recovery_code": "XQX-..." }`。

失败统一为 `invalid_recovery` 或 `rate_limited`；不得披露账号、恢复码哪一项错误。

#### `POST /functions/v1/account-delete`

需要登录态并再次验证当前密码。执行逻辑留至 M7 接入，但 M1 先预留认证、审计和二次确认参数结构。

## 5. 数据模型

### 5.1 公共枚举

```text
pet_action      = poke | slap | feed | throw
point_event     = welcome | pet_action | rant_publish | resonance_give |
                  resonance_claim | release_complete | checkin |
                  care_water | care_sit | pet_revive
rant_status     = pending | published | destroyed | expired | rejected
review_status   = pending | approved | rejected | hidden
care_type       = water | sit
```

### 5.2 核心表

#### `profiles`

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | uuid PK | 对应 Auth 用户 |
| `points_balance` | integer | 当前可用积分，非负 |
| `free_diy_available` | boolean | 注册权益；首次使用后为 false |
| `appearance` | jsonb | 含 `version` 的 8 维桌宠外观 |
| `pet_status` | jsonb | endure/irritate/fat/dirty/down/locked_until |
| `off_hour`, `off_min` | smallint | 下班时间，默认 18:00 |
| `created_at`, `updated_at` | timestamptz | 审计时间 |

#### `point_ledger`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | 流水 ID |
| `user_id` | uuid | 所有者 |
| `event_type` | enum | 积分事件类型 |
| `delta` | integer | 正负积分变化 |
| `idempotency_key` | text | 调用方/服务端唯一事件键 |
| `reference_type`, `reference_id` | text/uuid | 关联吐槽、共鸣、签到等 |
| `metadata` | jsonb | 安全的附加上下文 |
| `created_at` | timestamptz | 发生时间 |

唯一约束：`(user_id, idempotency_key)`；对服务端生成的全局事件键使用全局唯一索引。

#### `rants`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | 吐槽 ID |
| `owner_id` | uuid | 仅服务端/本人可见 |
| `content` | text | 纯文本，1–50 用户可见字符 |
| `status` | enum | 生命周期状态 |
| `review_status` | enum | 审核结果 |
| `votes` | integer | 有效共鸣总数 |
| `created_at`, `expires_at`, `destroyed_at` | timestamptz | 生命周期 |
| `release_rewarded_at` | timestamptz nullable | 防止释怀重复奖励 |

#### `resonances`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | 共鸣 ID |
| `rant_id` | uuid | 关联吐槽 |
| `actor_id` | uuid | 共鸣者，仅内部可见 |
| `owner_id` | uuid | 作者，仅内部可见 |
| `clicker_rewarded` | boolean | 当日是否给点击者奖励 |
| `owner_claimed_at` | timestamptz nullable | 作者是否领取 |
| `created_at` | timestamptz | 创建时间 |

唯一约束：`(rant_id, actor_id)`；检查约束：`actor_id <> owner_id`。

#### `checkins` / `care_completions`

分别记录服务端自然日签到和关怀完成事件。使用 `(user_id, business_date)`、`(user_id, business_date, type, sequence)` 等唯一键约束，避免刷新或并发重放得分。

#### `account_recovery_codes`

存储 `user_id`、`code_hash`、`created_at`、`revoked_at`、`used_at`。仅 Edge Function 通过 Service Role 访问。

#### `reports`

记录公开吐槽举报；包含 `rant_id`、举报者、原因、创建时间和处置状态。公开端不返回举报数据。

### 5.3 公共安全视图

建立 `public_rants_random` 受限视图/RPC，只能输出：

```json
{ "id": "uuid", "content": "...", "votes": 12, "created_at": "...", "expires_at": "..." }
```

禁止使用 `select *`，禁止暴露 `owner_id`、审核状态、销毁信息、内部评分或任何可关联用户身份的字段。

## 6. 统一积分规则与原子结算

| 行为 | 默认积分 | 服务端限制 |
|---|---:|---|
| 首次注册欢迎 | +300 | 每账号一次 |
| 首次注册免费 DIY | 免费 | 每账号一次 |
| 桌宠有效动作 | +10 | 由远端配置控制；倒地/锁定不奖励 |
| 公开吐槽审核入墙 | +50 | 每日 3 条 |
| 给他人有效共鸣 | +10 | 每天前 10 次 |
| 收到有效共鸣 | +10 | 待作者一次性领取 |
| 完整释怀 | +100 | 满 24 小时、看完、每条一次 |
| 每日签到 | +100 + 惊喜 | 每日一次 |
| 喝水 | +20 | 每日最多 6 次奖励 |
| 久坐 | +30 | 每日最多 4 次奖励 |
| 复活原领导 | -500 | 必须积分足够且处于倒地状态 |

所有规则读取服务端 `app_config`（或等价配置表）。前端可展示当前配置，但不得传入积分数值。涉及状态修改和积分变更的操作必须处于同一数据库事务中：

```text
验证身份 / 所有权 / 资格
  → 检查幂等键与每日上限
  → 修改业务状态
  → 写入 point_ledger
  → 更新 profiles.points_balance
  → 返回最终状态
```

## 8. 安全、审核、限流与数据生命周期

### 8.1 内容审核

发布请求按以下顺序处理：

1. 服务端规范化空白、检查 1–50 个用户可见字符与纯文本；
2. 检测手机号、邮箱、微信号、身份证号、详细地址、工号等可识别信息；
3. 检测禁止内容：违法、威胁、隐私、歧视、色情、诈骗、严重伤害性内容；
4. 通过时写入 `published/approved`，否则不入公开墙；
5. 原因返回使用安全、概括性代码，避免泄露审核规则细节。

客户端预检只改善体验，不具有安全权威性。

### 8.2 限流建议

| 接口 | 建议限流策略 |
|---|---|
| 注册 / 登录 / 找回密码 | 账号 + IP + 设备指纹分层；指数退避 |
| 发布吐槽 | 用户每日 3 条硬限制 + 短窗请求限流 |
| 共鸣 | 用户短窗限流 + 数据库唯一约束 |
| 桌宠动作 | 按用户、轮次和锁定期校验；可批量结算 |
| 积分和销毁 | 幂等键、事务、审计日志、异常告警 |

### 8.3 生命周期

- 公开吐槽创建时写入 `expires_at = created_at + 15 days`。
- 每次公开查询实时过滤 `published + approved + expires_at > now()`，不得只依赖定时任务。
- 定时任务清理到期原文或执行不可恢复匿名化删除；任务失败不应导致公开查询泄露过期内容。
- 用户注销时立即销毁该用户公开吐槽，按数据保留策略删除/匿名化个人数据。

## 9. 模块验收清单

### M0：工程与安全基线

- [ ] 迁移可在全新本地数据库重复执行；
- [ ] 前端环境变量只有匿名公钥与公开 URL，无 Service Role Key；
- [ ] 业务表开启 RLS，默认无直接写权限；
- [ ] 统一错误格式：`{ ok:false, reason:"...", request_id:"..." }`；
- [ ] 开发、测试、生产环境与密钥隔离。

### M1：账号与恢复码

- [ ] 合法账号可注册，重复账号不可注册；
- [ ] 注册原子生成档案、300 欢迎积分、免费 DIY 权益和恢复码哈希；
- [ ] 密码、恢复码不出现在数据库明文、错误响应或日志；
- [ ] 登录失败不枚举账号；
- [ ] 使用正确恢复码能重置密码并轮换恢复码；
- [ ] 错误/过期/已使用恢复码失败；
- [ ] 注册、登录、找回均可限流且返回安全错误。

#### 当前实现（2026-08-18，联调中）

- 迁移：`202608170002_m1_auth_and_profile_schema.sql`，以及恢复码保留锁修复迁移 `202608180003_m1_recovery_reservation_fix.sql`；
- 数据表：账号映射、最小个人档案、积分流水、恢复码、恢复保留锁、注册请求记录、认证限流；
- 内部 RPC：注册初始化、内部登录标识查询、恢复码保留/轮换、数据库持久化限流；

### 当前实现：M3 桌宠互动（开发中）

- 迁移：`202608180007_m3_pet_action.sql`。
- RPC：`m3_pet_action(user_id, pet_action, request_id)`。
- Edge Function：`pet-action`。
- Edge Function：`pet-revive`，登录态下复活倒地领导，服务端按 `points.pet_revive` 扣分并恢复满血状态；重复请求幂等。
- 服务端负责校验倒地、锁定、动作枚举、状态变化、积分配置、幂等键和最终余额；客户端只发送动作和请求 ID。
- `pet_status` 变化与 `point_ledger` 写入处于同一数据库事务；重复请求返回第一次结算结果，不重复加分。
- `slap` 锁定 5 秒；`feed` 达到胖度上限返回 `burst`；`throw` 达到脏度上限返回 `faint`；承受值归零后标记 `down`。
- 倒地状态不会因为登录、刷新或切换页面自动复活；P1 必须显示“复活 / 重新捏领导”入口。复活成功后才由服务端返回的新状态解除 `down`。
- 重新保存新的领导外观时，`m1_save_appearance` 同一事务会把桌宠重置为满血并解除 `down`，避免“重新捏完仍倒地”的状态残留。
- P1 的 2D 人物预览同步提供戳动、拍扁、喂食弹跳和扔东西甩动动画；不能只调用当前不可见的 3D Canvas 动画。

### 防回归规则（本次问题固化）

1. 弹窗遮罩点击不得默认关闭表单；关闭必须来自明确的关闭、取消或完成操作。错误信息优先显示在当前弹窗内部。
2. 登录态页面必须调用 `XQXAuth.profile()` 完成令牌刷新后再判断会话，禁止只检查原始 `localStorage` Token。
3. 账号名、积分、签到、DIY 权益、桌宠状态等正式数据不得使用 HTML 写死值；页面初始值只能是“读取中/--”，最终值必须来自云端。
4. 积分变化不得只修改前端变量；每次正式奖励必须有服务端事务和 `point_ledger` 唯一幂等键。
5. 每个新增 Edge Function 必须同时提交入口文件、前端调用适配、部署命令和至少一个重复请求/失效会话验收项。
6. 云端部署后必须做一次强制刷新和跨页面验证，避免把旧缓存误判为新代码。
7. 倒地提示只能在一次新的倒地状态中自动出现一次；用户主动打开复活入口不受此限制。
8. 登录、刷新或云端恢复 `pet_status.down=true` 只恢复历史倒地状态，不得把它当作新的倒地事件自动打开复活弹窗；复活请求失败也只显示当前弹窗内的错误，不得重复打开弹窗。
9. 签到后的下班节奏和关怀提醒属于前端时间体验，不能伪造积分；关怀积分仍必须通过 `care-complete` 服务端结算。
10. 登录视觉素材与认证逻辑分离；更换 GIF/WebP/PNG 只能修改公开视觉配置，不得把敏感配置或认证流程写入素材。
