## 4. 审核后台现状（当前暂缓）

### 已有功能

- P7 页面：`P7_审核后台.html`；普通用户导航没有入口。
- 审核账号在 P1 输入账号和密码登录成功后，由后端角色校验决定是否自动跳转 P7。
- 角色为 `moderator` / `admin` 的用户可读取举报队列并做出：`approved`、`hidden`、`rejected` 决定。
- 每次决定带 `request_id`，重复提交不会重复产生审核记录。
- P7 可显示最近审核处理摘要；不展示发布者、举报者、审核员身份或内部备注。
- P8 页面：`P8_角色管理.html`；仅管理员可用，支持授予/撤销 `moderator`，普通用户和 moderator 由服务端拒绝。

M8/P8 当前不阻塞核心上线。独立开发阶段不需要先建立审核员团队；上线初期可以由你本人通过受控管理方式处理极少量举报。只有后续举报量上升、需要委托他人审核时，才启用 P7/P8 并完成角色授予流程。
- 审核队列、审核决定和审核历史接口均已接入服务端持久化限流；限流配置不可用时接口明确失败，不会静默绕过安全策略。
- 核心接口自查补齐了修改密码、签到、工作节奏保存的服务端限流；三者超过频率都会返回 `rate_limited`，不会只依赖前端按钮状态。

### 已观测到的云端状态

曾使用普通已登录账号打开 P7，页面收到并正确显示“无审核权限”。这至少证明当前 Supabase 环境中的 `moderation-queue` 与角色校验链路可达，普通账号被后端拦截为 `403 forbidden`。

仍需明确验收或部署的部分：

- `moderation-review` 是否已部署并可真实写入审核决定；
- `202608210025_m8_moderation_history.sql` 是否已执行；
- `moderation-history` 是否已部署；
- 专用审核测试账号能否查看队列、处理内容并看到历史摘要。

### 审核角色原则

- 不在前端写审核账号名单；
- 不根据账号名判断权限；
- 不提供普通用户自助成为审核员的页面；
- 角色只由受控 Supabase 管理员在控制台对专用测试账号授予；
- 不在聊天、截图、提交信息、前端文件或日志中暴露真实 Auth User UUID。

## 5. 下次开始时的操作

### 5.1 同步和基础检查

在 Codespaces 执行：

```bash
cd /workspaces/XGX
git pull origin main
git log -1 --oneline
npm run check
```

`npm run check` 现在额外包含核心发布检查：确认 M1–M7 的 23 个 Function 同时存在于部署清单、源码和前端适配层，并确认暂缓的 M8 Function 没有混入核心部署。也可以单独运行：

```bash
npm run check:core
```

核心部署后可用一条只读命令确认公开接口连通且没有泄露内部字段：

```bash
npm run smoke:public
```

它只请求 `rants-random?limit=1`，不创建或修改业务数据；未配置公开 URL/anon key 时会明确提示，不会打印 key。

预期最新提交：


### 5.2 启动前端

```bash
npm run dev
```

根地址会固定打开 `P1_首页.html`，不用再手输首页文件名。纯前端改动后，停止旧服务并重启，再使用浏览器强制刷新：

```text
Ctrl + C
npm run dev
Ctrl + Shift + R
```

### 5.3 仅在确认需要时部署 Supabase

先检查本次 Git 更新是否包含 `supabase/migrations/` 或 `supabase/functions/`。只有两者变化时，才需要部署。

当前 M8 审核历史需要：

```bash
npm run supabase -- db push
npm run supabase -- functions deploy moderation-history
```

当前主线使用 M1–M7 核心部署命令，不把 M8 审核后台作为上线门禁：

```bash
npm run deploy:core
```

该命令会先运行检查，再执行数据库迁移和 23 个核心 Function 部署；它不会部署 `moderation-queue`、`moderation-review`、`moderation-history` 或 `moderation-role`。仅查看执行顺序时使用：

```bash
npm run deploy:core -- --dry-run
```

为了减少重复输入，也可以使用项目内置的一键部署命令：

```bash
npm run deploy:m8
```

它会按顺序执行项目检查、`db push` 和 3 个 M8 审核 Function 部署。它不读取或写入代码中的密钥；Supabase CLI 使用本地登录态。执行前仍需先完成一次：

```bash
npm run supabase -- login
```

只想检查命令顺序、不连接云端时：

```bash
npm run deploy:m8 -- --dry-run
```

若需完整核对 M8 审核模块，也可明确重新部署：

```bash
npm run supabase -- functions deploy moderation-queue
npm run supabase -- functions deploy moderation-review
```

部署命令不会要求将 `SUPABASE_SERVICE_ROLE_KEY`、数据库密码、`CRON_SECRET`、`RATE_LIMIT_SECRET` 或恢复码 pepper 写入前端或 Git。任何此类敏感内容都不能提交、截图或发送到聊天中。

## 6. 当前上线验收清单（M1–M7）

按以下顺序测试，发现问题只修对应模块后再继续。

1. 注册、登录、退出、刷新和失效 Token；错误提示留在当前弹窗。
2. 找回密码、修改密码、新密码登录和恢复码轮换。
3. 签到幂等：重复签到不重复加分，刷新后仍显示已签到。
4. 领导首次创建、动作、倒地、复活、倒地后重新捏；正常外观锁定。
5. 匿名发声每日上限、随机墙、共鸣唯一性和积分流水。
6. 举报自己、重复举报、三人举报自动隐藏；举报错误显示在弹窗内部。
7. 释怀销毁、24 小时奖励、未满足时间门槛时的 0 积分幂等处理。
8. 下班、喝水、久坐设置跨页面同步；重新登录不自动弹设置弹窗。
9. 注销测试账号：错误密码不删，正确密码后 Token 失效、数据级联删除、公开内容消失。
10. 过期内容：随机墙实时排除到期内容；定时任务执行后正文、共鸣和举报关联物理删除；重复任务安全跳过。

## 9. 项目约束与防回归规则

1. 浏览器仅使用 Supabase URL 与 anon/publishable key；禁止任何服务端密钥进入前端、仓库、截图和聊天记录。
2. 弹窗点击遮罩不得默认关闭；表单错误必须显示在当前弹窗内。
3. 正式积分、签到、共鸣、释怀、复活和注销只能以服务端返回结果为准，不能通过前端变量伪造成功。
4. 公开吐槽接口不得返回账号、`owner_id`、举报者、审核字段、恢复码或销毁信息。
5. 所有新增 Edge Function 需同步提供：前端调用、迁移/RPC（如需要）、部署命令、失效会话/重复请求验收项和文档。
6. 每次提交前运行 `npm run check`；完成云端部署后必须强制刷新并进行跨页面验证。
7. 不覆盖 Codespaces 中用户本地的 `scripts/xqx-config.js`；该文件可保存公开连接配置但不应提交敏感值。
