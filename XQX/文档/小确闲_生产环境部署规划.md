## 1. 部署目标与结论

小确闲 v1 的生产目标是：安全地提供匿名吐槽、账号认证、积分结算与 3D 前端体验，同时保证个人数据不因单台云服务器故障而不可恢复。

### 推荐的 v1 生产架构：混合托管

```text
用户浏览器
    │ HTTPS
    ▼
CDN / WAF（可选但推荐）
    │
    ▼
云服务器（Ubuntu LTS）
    ├─ Caddy / Nginx：TLS、静态页面、压缩、基础安全头
    ├─ 前端静态站点：P1–P6、Three.js 资源、版本化 assets
    ├─ 业务 API / Edge Function 网关：鉴权、限流、审计
    ├─ Redis：速率限制、短期幂等/会话辅助、任务锁
    └─ 监控代理：日志、指标、异常上报
    │
    ├──────────────────────────────► 对象存储（可选：备份、导出、静态大资源）
    │
    ▼
托管 Postgres + Auth（推荐 Supabase Cloud 或云数据库）
    ├─ profiles / rants / resonances / point_ledger
    ├─ RLS、认证、数据库备份
    └─ 定时任务 / Edge Functions（如采用 Supabase）
```

**推荐结论：** 首发阶段不要在同一台云服务器上自托管完整 Supabase 集群和生产数据库。服务器适合承载前端、反向代理、业务服务、Redis、监控和发布流程；认证与 Postgres 优先使用托管服务。

原因：小确闲包含密码、恢复码、积分流水和公开内容，数据库可靠性、备份恢复、鉴权配置、SMTP/令牌安全等风险远高于静态前端部署。自托管 Supabase 实际包含多个服务与大量运维责任，不适合在 v1 用单台服务器承载唯一生产副本。

## 2. 三种部署模式与选择

| 模式 | 描述 | 适用性 | 建议 |
|---|---|---|---|
| A. 混合托管 | 云服务器部署前端/API；Supabase Cloud 或托管 Postgres/Auth 处理数据与认证 | v1、团队规模小、需要快速可靠上线 | **推荐** |
| B. 托管 PaaS | 前端和 API 部署到 PaaS；数据库/认证继续托管 | 无运维人力、访问量早期不确定 | 可选 |
| C. 全自托管 | 云服务器/集群运行反向代理、API、Supabase、Postgres、Redis、监控、备份 | 有成熟运维、合规要求必须自控 | v1 不推荐 |

### 2.1 模式 A 的职责边界

| 组件 | 承载位置 | 职责 |
|---|---|---|
| Web 静态站点 | 云服务器 + CDN | HTML/CSS/JS、Three.js、版本化静态资源 |
| 业务服务 | 云服务器容器 | 未来自建 API、webhook、后台任务；或作为 Supabase Function 的补充 |
| 数据库、认证、RLS | 托管 Supabase/托管 Postgres | 密码认证、业务数据、积分原子事务、备份 |
| Redis | 云服务器容器或托管 Redis | 限流、幂等辅助、任务锁；不是唯一业务事实来源 |
| 文件/备份 | 对象存储 | 数据库逻辑备份、日志归档、导出文件 |
| DNS/TLS/WAF | 云厂商或 CDN | 域名解析、证书、DDoS/WAF、基础攻击防护 |

## 3. 域名、网络与访问拓扑

### 3.1 域名建议

```text
www.<主域名>       用户前端站点（HTTPS）
api.<主域名>       自建业务 API（若启用）
admin.<主域名>     管理后台；v1 可不开放公网或仅 VPN/IP 白名单
status.<主域名>    可选：状态页
```

数据库不使用公网泛暴露域名。若采用托管 Supabase，浏览器只访问其受控 API 地址；服务器使用受限服务端密钥访问服务端能力。

### 3.2 防火墙规则

| 端口 | 来源 | 目标 | 是否开放公网 |
|---:|---|---|---|
| 80 | 全网 | Caddy/Nginx | 是，仅用于跳转 HTTPS / ACME |
| 443 | 全网 | Caddy/Nginx | 是 |
| 22 | 固定管理员 IP 或 VPN | SSH | 否，禁止全网开放 |
| 3000/8000/5432/6379 | 仅 Docker 内部网络/私网 | API、Postgres、Redis | 否 |
| 监控端口 | 监控私网/IP 白名单 | 监控代理 | 否 |

必须关闭密码 SSH 登录，使用单独管理员账户、SSH Key、最小 sudo 权限和 fail2ban/云防火墙保护。生产主机禁止直接以 root 日常登录。

### 3.3 网络原则

- TLS 仅在反向代理层终止，站内服务保持私有 Docker 网络或私网访问；
- 数据库仅接受托管私网连接或受限 IP / TLS 连接；
- Redis 不暴露公网、不作为密码或积分的永久存储；
- 管理后台、数据库控制台和服务器管理面板不对所有公网 IP 开放；
- 回源仅允许 CDN/WAF IP 段时，可在应用层再加来源限制。

## 4. 服务器规格与扩容策略

### 4.1 v1 首发基线

适用于早期验证、日活处于低至中等规模、3D 渲染主要发生在用户浏览器：

| 资源 | 起步建议 | 说明 |
|---|---|---|
| 云主机 | 2 vCPU / 4 GB RAM / 60 GB SSD | 静态前端、反向代理、轻量 API、Redis、监控代理 |
| 操作系统 | Ubuntu 24.04 LTS 或同级 LTS | 长期安全更新与稳定生态 |
| 带宽 | 按峰值访问量选择；优先 CDN 缓存静态资源 | Three.js/字体等静态资源不要全部直出 |
| 数据库 | 托管 Postgres，至少开启 PITR 或每日备份 | 不与应用容器同机 |
| 对象存储 | 一个独立 Bucket | 逻辑备份、日志导出、可选静态大资源 |

### 4.2 触发扩容的信号

| 信号 | 首先采取的措施 |
|---|---|
| CPU 连续 15 分钟 > 70% | 扩容实例或拆分 API 进程 |
| 内存 > 75% / 频繁 OOM | 增加内存、限制容器、检查泄漏 |
| P95 API > 800 ms | 分析数据库/RPC、增加索引、缓存非敏感读取 |
| 带宽高 / 静态请求多 | 迁移图片/JS/字体到 CDN 或对象存储 |
| 数据库连接接近上限 | 使用连接池、缩短事务、限制并发 |
| 任务积压 | 单独部署 Worker 与队列，不在 Web 进程内长时间执行 |

## 5. 容器与进程编排

### 5.1 v1 建议容器

```text
reverse-proxy      Caddy 或 Nginx，唯一公开入口
web                静态前端（可由 reverse-proxy 直接提供）
api                自建业务 API（若使用；否则由 Supabase Functions 承担）
worker             定时/异步任务（后续需要时再启用）
redis              限流、任务锁、短期缓存
monitoring-agent   日志和指标收集
```

所有容器必须：

- 使用固定镜像版本或可追溯 digest，禁止生产环境无版本 `latest`；
- 配置健康检查、内存/CPU 限额和只读文件系统（可行时）；
- 以非 root 用户运行；
- 通过 Docker secrets / 云密钥服务注入密钥，禁止把 `.env` 写入镜像或仓库；
- 仅 `reverse-proxy` 绑定公网端口；
- 写入 stdout/stderr，交由日志系统收集，避免容器内无限增长日志文件。

### 5.2 反向代理必须提供的安全能力

- HTTP 自动跳转 HTTPS；
- 自动证书续期、TLS 1.2+、HSTS；
- gzip/brotli 压缩与静态资源强缓存；
- CSP、`X-Content-Type-Options: nosniff`、`Referrer-Policy`、`Permissions-Policy`；
- API 请求体大小上限、读取/写入/上游超时；
- 针对登录、找回、发布、共鸣端点的网关级基础限流；
- 访问日志中脱敏 `Authorization`、Cookie、密码、恢复码与请求体。

### 5.3 CSP 首发建议

当前前端直接使用 Google Fonts 与 unpkg Three.js。生产前应优先将 Three.js、字体和依赖版本化后本地托管或放入受控 CDN。

在完成本地化前，CSP 必须显式白名单所需域名；完成本地化后，目标 CSP 为：

```text
default-src 'self';
script-src 'self';
style-src 'self';
img-src 'self' data:;
connect-src 'self' https://<supabase-api-domain>;
font-src 'self';
object-src 'none';
base-uri 'self';
frame-ancestors 'none';
form-action 'self';
```

现有页面包含内联脚本和样式，不能直接套用严格 CSP。上线前需将它们迁移到版本化外部资源，或短期使用 nonce；禁止以长期 `'unsafe-inline'` 作为最终方案。

## 6. 密钥、配置与权限

### 6.1 配置分层

| 环境 | 目的 | 数据隔离 |
|---|---|---|
| local | 本地迁移、函数与前端联调 | 本地容器/本机密钥 |
| staging | 部署前集成测试、灰度验证 | 独立项目、独立数据库和独立密钥 |
| production | 正式用户流量 | 独立项目、独立域名、独立密钥 |

生产数据严禁复制到 local/staging；若需要调试，只允许去标识化、最小化样本。

### 6.2 密钥规则

- `SUPABASE_SERVICE_ROLE_KEY`、恢复码 pepper、内容审核 Key、Redis 密码仅放入密钥服务或服务器受限环境；
- 前端仅可见 `SUPABASE_URL`、匿名公钥、公开 Sentry DSN 等非敏感配置；
- 每个环境使用不同密钥；人员变动、泄露疑虑或服务器事件后立即轮换；
- CI/CD 使用部署专用服务账号，禁止复用个人 SSH Key；
- 定期检查 Git 历史、容器镜像、日志、监控标签中是否包含密钥或 PII。

## 7. 数据库、备份与恢复

### 7.1 数据库要求

- 生产 Postgres 与应用服务器分离；
- 开启加密传输（TLS）与静态加密；
- 使用连接池，避免每个网页访问建立新连接；
- 迁移仅由 CI/CD 或受控运维账户执行；
- 所有积分、复活、共鸣、销毁、签到事务记录唯一事件键；
- 每周检查慢查询、索引命中、连接数与失败事务。

### 7.2 备份策略

| 数据 | 方式 | 频率 | 保留 | 恢复目标 |
|---|---|---|---|---|
| Postgres | 托管 PITR + 加密逻辑备份到对象存储 | PITR 连续；每日逻辑备份 | 30 天起 | 恢复到指定时间点 |
| 迁移/函数/部署配置 | Git 私有仓库 + CI Artifact | 每次发布 | 长期 | 任意版本重建 |
| 服务器配置 | 加密配置备份/IaC | 每次变更 | 长期 | 新机重建 |
| 访问日志 | 集中日志平台 | 实时 | 7–30 天，按合规调整 | 事故排查 |

备份只有验证过恢复才有效。上线后至少每季度做一次演练：从备份恢复到隔离环境，核验用户表、积分账本、迁移版本与公开数据过滤规则。

### 7.3 恢复优先级

1. 阻断泄露、下线异常版本、轮换密钥；
2. 恢复认证和数据库可用性；
3. 验证积分账本余额与关键流水一致；
4. 恢复公开吐槽过滤，确保不泄露销毁/过期内容；
5. 恢复前端与非关键分析；
6. 形成事故报告与修复迁移。

## 8. 可观测性、告警与审计

### 8.1 必须采集的指标

- HTTP 请求量、2xx/4xx/5xx、P50/P95/P99 延迟；
- 登录/找回/注册失败率与限流命中；
- 发布吐槽、共鸣、释怀、签到、桌宠动作的业务成功率；
- 积分事务失败、重复幂等键、余额异常、复活失败；
- 主机 CPU/内存/磁盘/网络、容器重启、Redis 内存；
- 数据库连接、慢查询、锁等待、备份成功/失败；
- 内容审核拒绝率和举报积压。

### 8.2 告警分级

| 等级 | 示例 | 处理目标 |
|---|---|---|
| P0 | 密钥泄露、数据库不可用、身份鉴权全面失效、公开泄露身份字段 | 立即响应、先止血 |
| P1 | 5xx 持续升高、积分重复/丢失、备份失败、登录失败率异常 | 30 分钟内响应 |
| P2 | CPU 高、慢查询、审核积压、磁盘容量不足 | 当日处理 |
| P3 | 文案/前端非阻断错误、可优化性能项 | 排入迭代 |

### 8.3 日志脱敏

严禁记录：密码、恢复码、Authorization、Cookie、完整 IP、完整吐槽原文与可识别信息。业务日志只记录请求 ID、匿名用户 ID 哈希、事件类型、结果、耗时和必要的错误码。

## 9. 发布、灰度与回滚

### 9.1 CI/CD 流程

```text
提交 PR
  → 格式化 / 静态检查 / 单元测试
  → 数据库迁移测试（全新库 + 升级路径）
  → Function/API 集成测试
  → 构建不可变前端与容器镜像
  → 部署 staging
  → 冒烟测试：注册、登录、桌宠、吐槽、共鸣、释怀、签到
  → 人工批准
  → 部署 production
  → 发布后监控与回归检查
```

### 9.2 生产发布规则

- 数据库迁移必须向前兼容：先加字段/表和双读写，前端发布后再清理旧结构；
- 迁移前自动备份并记录迁移版本；
- 静态资源使用内容 hash，HTML 短缓存，JS/CSS 长缓存；
- 新功能使用服务端 feature flag；
- 首次真实发布优先小流量灰度或邀请制；
- 回滚时优先回滚应用版本，不随意回滚已执行的破坏性数据库迁移；必要时提供前向修复迁移。

### 9.3 上线冒烟测试

- HTTPS、重定向、证书、CSP、安全头；
- 试用态与登录态边界；
- 注册后 300 分和免费 DIY 仅发一次；
- 桌宠动作、锁定、倒地、复活扣 500 分事务正确；
- 发布上限、匿名公开字段、审核拦截、15 天过滤；
- 共鸣唯一性、作者领取、销毁 24 小时奖励幂等；
- 签到/关怀每日上限；
- 备份任务、监控告警、日志脱敏；
- 桌面与移动主流程、减少动态效果模式。

## 11. 待确认项

以下事项会影响实际配置，但不影响当前 M0–M1 的代码设计：

1. 云厂商和地域：优先选择目标用户所在地网络体验和数据合规可接受的地域；
2. 是否使用 Supabase Cloud，还是采用同等能力的托管 Postgres/Auth；
3. 域名与是否接入 CDN/WAF；
4. 管理员访问是否具备固定 IP 或 VPN；
5. 内容审核服务供应商与审核策略；
6. 告警接收渠道（邮件、企业微信、钉钉、Slack 等）；
7. 是否需要符合特定备案、隐私、数据跨境或行业合规要求。

在这些项目确定前，不创建生产资源、不提交真实密钥、不部署任何公开服务。
